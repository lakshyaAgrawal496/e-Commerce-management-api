Release Inventory

Q.What is GIL?
GIL = Global Interpreter Lock.
In CPython (the standard Python implementation), the GIL is a lock that ensures that only one thread at a time executes Python bytecode inside a process. The GIL protects CPython interpreter state while Python bytecode is executing.
Need the GIL?
The biggest reason is memory management, especially reference counting.
Now imagine two threads simultaneously manipulating references to the same object.
Thread 1                 Thread 2
   │                        │
   ▼                        ▼
increment refcount      decrement refcount
If both modify the same counter concurrently without synchronization, you can get a race condition.

The GIL prevents multiple threads from simultaneously executing Python bytecode in the same CPython process.
CPython periodically switches between threads and can release the GIL during blocking operations or when native code explicitly releases it.
Thread 1
   │
   ├── waiting for network
   │
   └── GIL released
              │
              ▼
         Thread 2 gets GIL
              │
              ▼
         executes Python

CPU-bound → multiprocessing on different CPU cores
I/O-bound → asyncio or threading 
                CPython
                    │
                  GIL
                    │
             controls THREADS
                    │
                    ▼
              Event Loop
                    │
             schedules TASKS
                    │
                    ▼
               await()
                    │
          voluntarily yields
                    │
                    ▼
          another TASK runs

In asyncio, when a coroutine reaches an I/O await, it suspends and gives control back to the event loop, which can run another coroutine on the same thread. The GIL still exists in traditional CPython, but the switch between asyncio tasks is not a GIL handoff; it is cooperative coroutine scheduling.
GIL: "Which thread can execute Python bytecode?"
Event loop: "Which coroutine/task should run on this thread?"
await: "This coroutine can't continue right now; give control back to the event loop."

Asyncio is designed for cooperative I/O concurrency. If a CPU-bound operation runs directly on the event-loop thread, it blocks the entire event loop because the coroutine doesn't yield. We should offload CPU-bound work to a process pool or external worker. A thread pool can keep the event loop responsive, but under the traditional CPython GIL it generally doesn't provide true parallelism for pure-Python CPU-bound work

Q.Routing-workflow?
When the application starts, FastAPI registers the routes from each APIRouter with the application. Each registered route contains its path, HTTP methods, and a reference to its endpoint function. At request time, Starlette's routing system matches the incoming HTTP method and path against the registered routes. Once a route matches, the route already knows which endpoint function it is associated with, so the router file itself does not need to be searched.

   ↓

   └── endpoint = search_products  ← actual Python function
                         │
                         │
app.include_router()

                FastAPI application
                         │
                         ↓
              registered routes

                         ↓

Q.Middleware?
Middleware is a component that wraps a downstream ASGI application and can process requests before passing them downstream and responses while they return. In FastAPI/Starlette, I would distinguish middleware by abstraction level rather than calling low-level and high-level formal types. At the low level, middleware works directly with the ASGI interface — scope, receive, and send. It can be implemented as a callable class or function and is useful when we need protocol-level control, such as intercepting ASGI events or handling HTTP/WebSocket/lifespan behavior. At a higher level, FastAPI/Starlette provides an HTTP middleware abstraction through @app.middleware("http"), where we work with a Request object and call_next. This is convenient for common HTTP concerns like logging, timing, request IDs, headers, and metrics. Class-based middleware is an implementation style, not a separate abstraction level; app.add_middleware() registers such middleware into the ASGI middleware stack.

Q.Can GET technically have a body?"
"HTTP does not universally prohibit a GET request from carrying content, but GET request bodies have no generally defined semantics in HTTP and intermediaries/frameworks may not handle them consistently. For API design, query/path parameters are normally used for GET."

Q.Does FastAPI enforce POST = create, PUT = update, DELETE = delete?
"No. FastAPI/Starlette enforce the registered HTTP method during route matching, but they don't enforce what business operation the endpoint performs. GET/POST/PUT/DELETE have defined HTTP semantics that we should follow when designing the API, but the framework doesn't inspect our endpoint implementation and prevent us from performing a different operation.
